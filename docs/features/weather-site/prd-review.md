# PRD 质检报告

## 总体评分：需要修改 ⚠️

审查日期：2026-10-16。依据：本地 prd.md v1.0、user-research.md、issue 原始需求及触发评论。两份上游文件均读取成功。本报告为文档静态审查，未执行产品或供应商实测。

PRD 已具备问题陈述、6 项 Non-Goals、量化验收指标、6 个 P0 用户故事、状态机、权限矩阵、发布计划与回滚条件；原始核心需求均有覆盖。不存在关键章节整体缺失，但以下规则和决策未闭环，不能直接作为最终研发及发布验收基线。

## 阻断问题（必须修复）

1. **B01｜预报异常数据处理冲突（§4 US-03、§7.3）。** US-03 将高低温矛盾、冲突重复日期判为“该日数据无效”，§7.3 却写“该日相应数据无效”。这会导致一种实现清空当天所有字段，另一种保留天气状况或温度。建议明确字段级/整日级规则，以及完全相同的重复日期如何去重。验收夹具：同日两条冲突记录；同日完全相同记录；最高温低于最低温但天气状况有效；逐项写明保留字段、占位和最终区块状态。

2. **B02｜ready/partial/error 判定口径不唯一（§5.2、§7.2、§7.3）。** “当前五项完整”即可 ready，但更新时间和时区均标为必填；“至少一个有效字段/日期”可能把系统生成的五个日期占位算作有效数据，与“无任何有效字段/日期按 error”冲突。建议规定有效数据只计上游有效气象字段，明确时间元数据是否影响完整性；生成的日期标签不得使全空预报成为 partial。验收：五指标齐全但无更新时间/时区；五日日期都有但所有天气字段为空；仅一天仅一项有效，各给唯一状态和重试行为。

3. **B03｜P0 验收基线尚未冻结（§4、§11 OQ-01/02/03/05/06/07/11）。** 手动选城、单位舍入、超时、浏览器矩阵及其他 P0 细则仍为建议。开放问题有负责角色和相对门禁，但缺少可执行的批准记录，开发和 QA 无法统一判定通过。建议在进入相应设计/实现前建立决策表，记录批准值、决策人、确认日期与适用门禁；无需为文档审查虚构上线日期。已明确的当地明日起连续五日不得降为可选范围。

4. **B04｜匿名代理防滥用要求未形成强制验收（§4 US-06、§8、OQ-04/06/08）。** 密钥服务端保管和错误脱敏充分，但服务端参数校验、上游目标限制仍标为建议，匿名公开接口可能消耗付费额度。建议将拒绝非法 city_key/参数、禁止客户端指定上游地址、服务端配额保护列为硬门禁；阈值由套餐配额确定，无需在本报告编造数值。验收应覆盖直接绕过 UI 请求、非法参数、任意 URL 参数、达到批准额度后拒绝且不继续调用供应商、恢复与错误脱敏。该项为发布阻断，不声称已发现实际漏洞。

5. **B05｜性能及数据新鲜度缺少可测试边界（§2.2、OQ-06）。** 10s 是等待截止时间，不能代替 P95 响应目标；缓存 TTL 被列入待定，但供应商直接返回的过旧“当前天气”也没有判定规则。建议由 RD/PM 在性能与接口评审前补充测试环境、并发/请求规模、计时边界、P95 目标，以及观测数据允许年龄、未来时间容差和超限提示/降级规则；明确不启用缓存时仍适用。验收注入过旧、未来和缺失时间戳，并在批准负载下验证耗时。不要求气象精度保证。

6. **B06｜跨午夜后完整结果缺少明确刷新路径（§7.2、§7.3）。** PRD 规定午夜不自动更新，且“下次查询/重试更新范围”，但重试按钮仅在 error/partial 可用，ready 状态没有刷新入口。用户可重新搜索并再次选城，但是否允许重选当前城市触发新查询未明确，容易出现停留页面无法直接更新日期范围的实现。建议明确 ready 状态的手动刷新入口，或明确重新搜索并重选同一城市必定发起新查询；当前与预报独立重试时明确 reference_at 的归属。验收：当地 23:59 完整加载后跨到次日，先保持原范围并标注查询基准，再通过指定入口刷新，五日范围前移一天且旧响应不能覆盖。无需新增自动轮询。

以上为局部规则与阶段门禁问题，故判为“需要修改”，不判为关键章节缺失的“重大问题”。供应商套餐、授权、部署能力与负责人仍须按已有 OQ-04/08/10 在对应门禁关闭。

## 建议改进

1. 为 US 验收条目增加稳定编号，并建立“原始需求—US—夹具—验收结果”映射，方便修改后回归。
2. 明确 Unicode 字符计数单位及负数恰好半值的舍入规则；补充 emoji、组合字符、-1.5°C、负零夹具，避免前后端实现不同。
3. 为首次无城市、全候选禁选、限流冷却和部分失败补充文案与可访问反馈示例；保留目前完整的键盘与触屏要求。

## 发现的歧义（表格）

| 位置/原文 | 不确定点 | 建议明确 |
|---|---|---|
| §4 “该日数据无效” / §7.3 “该日相应数据无效” | 整日还是字段失效 | 统一异常字段保留规则，见 B01 |
| §5.2 “至少一个有效字段/日期” | 日期占位是否算有效天气 | 定义有效气象字段与状态真值表，见 B02 |
| §5.2 “当前五项完整” / §7.2 时间元数据必填 | 缺时间能否 ready | 明确完整性判定与提示，见 B02 |
| §7.1 country 必填，但“缺失且无法区分时不可选择” | 缺国家但可区分能否选 | 规定必填缺失的唯一处理，纳入 OQ-11 |
| §7.1 “全部候选结构无效” | 全部禁选是否等同结构无效 | 区分服务错误与可修改查询的无可选结果 |
| §7.4 “有冷却时间时”及 retry_after | 非法值、过期值、超长值的行为 | 确认解析、默认值、上限和计时依据 |
| §4 “四舍五入”、Unicode 字符 | 跨语言实现边界不同 | 补精确计数及舍入夹具 |
| §2.2 “至少一区块可用” | partial 是否纳入成功；被取消查询如何计分母 | 明确统计公式，分子分母均排除失效版本 |

未发现需要单纯替换“友好的”“合适的”等修饰词的主要问题；关键歧义集中在状态定义、异常粒度和待批准参数。

## PM 视角 Review

- **最可能超期：** 供应商同时满足城市检索语言、重名消歧、当前五项指标和“明日起五日”的能力验证。建议先做能力矩阵和真实样例验证，再完成接口契约及估算；不通过时重新选型或回到产品评审，不能静默缩范围。
- **容易低估：** 服务端代理不是只隐藏密钥，还涉及匿名调用配额保护、秘密注入与轮换、错误脱敏及运行监控；时区和午夜重试也需真实供应商数据验证。
- **跨团队依赖：** 产品负责人批准范围与预算；RD 负责供应商适配和服务端方案；部署维护者负责凭据与回滚；设计/QA 冻结兼容矩阵和验收夹具。PRD 已识别这些角色，但仍需指派实际责任人及完成时点。
- **范围一致性：** 无账号/定位/单位切换与当前故事一致；全部候选手动选择较上游“单一精确候选可自动查询”更严格，PRD 已透明列为 OQ-02，不视作已批准决定。
- **发布控制：** 已有密钥泄漏、城市串位、日期错位硬回滚条件，方向正确；运行阈值与灰度能力仍为建议，应在发布评审前批准，首次发布无健康版本的维护页路径应演练。

## 结论

**需要修改 ⚠️。** 建议需求撰写师修复 B01/B02 的规则冲突，补齐 B03 的决策基线及 B04/B05 的安全、性能和新鲜度验收门禁，并修复 B06 的跨午夜刷新闭环，再交质检复审。无需重写完整 PRD；可继续供应商可行性验证和依赖澄清，尚不能宣称需求已通过并具备发布条件。
